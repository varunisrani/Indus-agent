# P04 · Turn loop and tool contract

**Weeks:** 7–8 (2 weeks) · **Track:** B (Python; one TS codegen slice) · **Depends on:** P02 (state store), P03 (providers + fake model); uses P00 guards and the D-04.1 trial harness, P01 `Scope`/config/clock/logging · **Status:** done (Agent 2, waves 5–6b)

## Goal
A Python caller can create a session through `SessionService`, submit a message, and watch the
agent stream text, call registered tools and finish, all against the scriptable fake model from
P03. The prompt is built once, stored with the session and reused byte for byte on resume; every
failure path (interrupt, bad tool name, malformed arguments, crash at any step) leaves a valid,
strictly alternating transcript with exactly one result per tool call; the user row and each
tool-call row are on disk before the side effects they precede. The declared protocol package
(`indus.protocol`) and its generated TypeScript (`packages/protocol`) exist, so the frontend track
can build against real types. The phase closes by recording the **D-04.1** verdict (asyncio core
kept, or the threaded fallback taken) in `docs/notes/P04/d-04-1-decision.md`.

Interop note: JSON-RPC 2.0 framing (`jsonrpc`, `id`, `method`, `params`, `result`, `error`
with `code`/`message`/`data`) is a third-party standard; check the envelope models against the
JSON-RPC 2.0 specification text, not against the reference. OpenAI-style tool schemas
(`{type: "function", function: {name, description, parameters}}`) and the
`tool_calls`/`tool_call_id` message fields are vendor wire shapes owned by P03's transports; this
phase only produces and consumes the provider-neutral form P03 defines.
