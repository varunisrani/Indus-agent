# P09 · Learning loop

**Weeks:** 2 · **Track:** B (backend, Python) · **Depends on:** P08 (compression rebuild of frozen blocks, the auxiliary model client P08-17 used by every side task here, usage rows), P06 (slash registry, REPL), P05 (tool registry, file read/search tools, approvals, env builder), P04 (prompt builder, `SessionService`, turn finalizer), P02 (store) · **Status:** planned

## Goal
The agent remembers and improves between sessions. Two bounded memory stores render into the
prompt as a frozen block; the agent writes them with the `memory` tool. Skills live as folders with
`SKILL.md`, appear as a compact index in the prompt, open on demand (`skills_list`, `skill_view`),
run as `/skill-name` slash commands and are written by the `skill_manage` tool. A background review
fork saves facts and improves skills after busy turns; `/refine` and `/learn` run it on demand. An
idle-time curator ages agent-made skills to stale and archived (never deleted), and about fifteen
starter skills we wrote ourselves are seeded into each profile. This proves the M2 claim "a skill
written by the review fork appears in the next session" and "memory writes never change the
current session's prompt".

Not in this phase (owned elsewhere): external memory providers, the skills hub, the shared content
scanner and project-skill trust/quarantine (P13); the cron store that the curator's protection rule
reads (P14 registers itself as a reference source, see P09-18); gateway "memory updated" chat lines
(P15 renders the summary built in P09-16); TUI and desktop learning views (P12, P20).
