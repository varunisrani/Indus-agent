What it does (own words): two more generated JSON twins on the one-shot start-up path, built the
way the wave-48 pricing and field-doc twins are (the source stays the source; the twin carries a
digest; a missing or stale twin costs time, never a wrong answer; a generator with `--check`; the
`generated_twins` guard runs every `--check`).

1. **Config defaults.** `foundation.config.schema` builds `DEFAULTS` from `ConfigModel()` at
   import, which forces pydantic to build every config section's validator (~200 ms of import
   here), and `loader.load` then validates the whole merged tree with `ConfigModel`. Now the
   section models are deferred (`defer_build=True`, built on first use), `DEFAULTS` is read from
   `foundation/config/defaults.json` while its sha256 of `schema.py` + `versions.py` matches (else
   `_build_defaults()` as before), and `validate()` checks only the top-level settings whose value
   is not exactly (type and value) the default; the defaults are valid by construction (pinned by a
   test), and anything unusual (a key spelled by field name where an alias exists) takes the old
   whole-model path. Warnings are the same text in the same order as the whole-model check.
2. **Shipped-skill front matter.** Every run parses the front matter of the 15 shipped skills (the
   copies seeded into `<home>/skills`) with the pure-Python YAML loader, ~20 ms. Now
   `learning/skills/shipped_frontmatter.json` maps the sha256 of each shipped `SKILL.md` front-matter
   block to its parsed mapping; `split_frontmatter` looks the block's digest up first and parses
   YAML only on a miss. Keyed by content, so an edited copy, a user skill or a changed shipped
   skill simply misses; a stale twin can never hand back another text's values.

Inputs → outputs: `uv run python -m indus.foundation.config.defaults_twin [--check]`,
`uv run python -m indus.learning.skills.frontmatter_twin [--check]` → the two JSON files (exit 1
with "is stale" on `--check`). Runtime: same `DEFAULTS`, same `validate()` warnings, same
`ParsedSkill` values, less time.

Files: `src/indus/foundation/config/schema.py`, `.../config/defaults_twin.py`,
`.../config/defaults.json`; `src/indus/learning/skills/format.py`,
`.../skills/frontmatter_twin.py`, `.../skills/shipped_frontmatter.json`;

Edge cases / failure modes:
- twin missing, unreadable, not JSON, wrong shape, digest mismatch → slow path (logged at debug);
- CRLF checkout: sources read as text (universal newlines), so the digest matches either way;
- a default that JSON cannot carry exactly (tuple, set, date): the generator refuses, so a twin
  never changes a type; front matter that JSON cannot carry exactly (a YAML date) is left out
  of the skills twin and parsed as before;
- `1 == 1.0 == True` in Python: "unchanged from the default" compares type and value, so `0`
  for a bool setting is still validated;
- a caller mutating `ParsedSkill.raw`: each hit hands out a fresh copy.

Our design differences / decisions:
- `W50-f-1` config defaults twin + deferred section models + validate only changed settings.
- `W50-f-2` shipped-skill front-matter twin keyed by the block's digest (not by path).
- `W50-f-3` both twins in the `generated_twins` guard; the guard's test fixture also copies
  `skills/` (the skills generator reads the shipped tree).

Tests we will write:
- config twin fresh (`--check` 0), equals `_build_defaults()` exactly (types too); import reads the
  twin and builds no config validator; stale / missing / broken twin → same `DEFAULTS` built from
  the models; `validate(DEFAULTS) == []`; `validate()` equals the whole-model check on a table of
  valid, invalid, unknown-key, union and alias inputs.
- skills twin fresh; covers every shipped skill; a shipped skill's front matter comes from the
  twin without a YAML parse (counted) and equals the parsed one; an edited block is parsed;
  hits are independent copies; broken twin → parsed.
- guard: both new twins checked; a stale one of each fails.
- one-shot probe: importing the one-shot modules builds no config section validator.

## Decisions for the lead
- **W50-f-1** (D-16.1174) config defaults twin. `_Section` and `ConfigModel` set `defer_build=True`;
  `DEFAULTS` comes from `foundation/config/defaults.json` while its `source_sha256` (sha256 over
  the names and texts of `schema.py` and `versions.py`, read as text) matches, else from
  `build_defaults()` (was `_build_defaults`, now public for the generator). `validate()` skips
  every top-level setting that is absent or `same_value` as its default and validates each other
  one with a per-setting `TypeAdapter` (the field's annotation plus its constraint metadata, built
  on first use and kept); `_validate_whole()` is the old whole-model check, kept for a key spelled
  by field name where an alias exists (`config_version`) and as the oracle the tests compare
  against. Any edit to `schema.py` (comments too) makes the twin stale: regenerate with
  `uv run python -m indus.foundation.config.defaults_twin` (the guard says so).
- **W50-f-2** (D-16.1175) shipped-skill front-matter twin keyed by the sha256 of the front-matter block (not by
  path): `format.split_frontmatter` → `frontmatter_block` (the fence split, factored out so the
  generator splits the same way) → twin lookup → YAML only on a miss; hits are deep copies. The
  generator reads `bundled_source({})` (never `INDUS_BUNDLED_SKILLS`) and exits 2 when there is
  no shipped tree; front matter JSON cannot carry exactly goes to `skipped` (none today).
- **W50-f-3** (D-16.1176) both generators in `tooling/checks/generated_twins.py` (now four twins); the guard
  test fixture copies `skills/` beside `src/` because the skills generator reads it; `biome.json`
  skips the two new generated JSON files like the existing twins (D-16.1102).
- Budgets unchanged (`tooling/perf/budgets.toml` untouched).
