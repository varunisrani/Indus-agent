What it does (own words): an attached TUI talks to the daemon over its WebSocket. Its `!command`
(and `{!command}` inside a prompt) calls `shell.exec`, which the daemon did not serve (`-32601`);
quick commands of type `exec` were refused by the daemon (W48-h-2) and marked `unavailable` in its
catalogue, so they were not offered. Now the daemon serves `shell.exec` and runs quick `exec`
commands with exactly the rules `--local` uses: the same dangerous-command detection (a hardline or
dangerous command is refused with `SHELL_REFUSED`, no approval card: the agent is the place for
those; a detector that cannot load refuses), the environment from the one builder
(`safety.child_env`, the connection's profile scope, provider keys out, the session's pins), stdin
from the null device, its own process group, the 30 s limit on the scope's clock (`SHELL_TIMEOUT`),
redaction before the tail cut (4 000 / 2 000 characters). The command runs in the session's folder
when it names one, else the profile's `terminal.cwd`, else the daemon's own folder (the same order
as the bridge, where the last step is the bridge's folder). A named session must be one this
connection attached (B-DAEMON-5): another connection's session reads `SESSION_NOT_FOUND`.

Inputs → outputs: `shell.exec {command, session_id?}` → `{stdout, stderr, code}` or `TEXT_EMPTY`,
`SHELL_REFUSED`, `SHELL_TIMEOUT`, `SESSION_NOT_FOUND`; `command.dispatch` of a quick `exec` name →
`{kind: exec, output}` (output and `(exit N)` as in `--local`); `commands.catalog` lists quick
`exec` commands `server` (no longer `unavailable`) and `complete.slash` offers them.

Files: `src/indus/service/host_shell.py` (new: the checks, runner and clean-up written once),
`src/indus/tui_bridge/methods_shell.py` (the bridge's handler over it), `src/indus/service/daemon_slash.py`
(`run_quick`, no refusal), `src/indus/service/picker_reads.py` (`DAEMON_QUICK_EXEC` gone),

Edge cases / failure modes:
- empty or blank command → `TEXT_EMPTY` (path `command`) before anything runs;
- hardline / dangerous → `SHELL_REFUSED` with the reason; detector import or check failure → refused;
- environment builder failure → `SHELL_REFUSED`, nothing runs;
- a command that never ends → killed (process group) at the limit, `SHELL_TIMEOUT "stopped after 30 s"`;
- huge output → only the redacted tail; a token crossing the cut never survives as halves;
- a foreign or unknown session id → `SESSION_NOT_FOUND` (never runs in another viewer's folder);
- a session whose folder vanished → falls back to `terminal.cwd`, then the daemon's folder;
- quick `exec` command with an empty `command` → `TEXT_EMPTY`, as in `--local`;
- Windows: the runner already uses `shell=True` and `proc.kill()` off POSIX (unchanged code moved).

Our design differences / decisions:
- W50-b-1 (D-16.1157): one definition (`service/host_shell.py`) for both hosts; the gateway may not import
  `tui_bridge`, so the bridge's handler now delegates to the service module (no behaviour change).
- W50-b-2 (D-16.1158): the daemon serves `shell.exec` to any connection that passed the ticket check (every
  attached client is the owner, B-DAEMON-2), with no rule looser than `--local`; a named session is
  checked against the connection's attachments like every other session-addressed call.
- W50-b-3 (D-16.1159): the folder order is the bridge's (session folder, `terminal.cwd`, the host process's
  folder); on the daemon the last step is the daemon's folder, which is also where the agent's own
  local terminal runs for a session with no folder.
- W50-b-4 (D-16.1160): protocol: `shell.exec` declares `SESSION_NOT_FOUND`; quick `exec` commands are no longer
  `unavailable` on the daemon (`DAEMON_QUICK_EXEC` removed, W48-h-2's quick `exec` part closed).
- Not taken: an approval card for a dangerous `!command` (the reference and `--local` refuse; a
  card would be a new path); running through the profile's sandbox backend (the bridge runs the
  owner's own command on the host, B-SHELL-1; the daemon does the same).
