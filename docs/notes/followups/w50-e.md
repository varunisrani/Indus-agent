What it does (own words): wave 49 gave a canary build its own app id, product name, Linux
executable and feed at packaging time (`scripts/channel-identity.cjs`), but the running app still
called itself `Indus` and wrote its Linux launcher entry as `ai.indus.desktop.desktop` with icon
`ai.indus.desktop` — so a canary AppImage overwrote the stable app's menu entry, and its windows
were grouped under the stable launcher. Now the running app takes its identity from the build
stamp's channel through the same derivation: a canary is named `Indus Canary` (window title, app
menu, `app.setName`, the launcher entry's Name and StartupWMClass) and its launcher entry and icon
are `ai.indus.desktop.canary`. The staged `package.json`'s `desktopName` (which Electron hands to
the desktop as the app's desktop-file id) follows the stamp's channel too.

Windows: electron-updater checks an NSIS update's Authenticode signer against `publisherName` in
`app-update.yml`, and electron-builder only writes that key when it knows a publisher. Without it,
the check is silently skipped. The config now keeps `verifyUpdateCodeSignature` on and gives
electron-builder the channel's configured publisher (the certificate subject recorded in
`packaging/msix/identity.json`, the same value the MSIX lane signs with). While that value is the
owner placeholder, a signed Windows build is refused before anything is built (a feed that names a
placeholder publisher would refuse every later update); an unsigned build keeps the placeholder,
which can never match a real certificate (fails closed).

Inputs → outputs: build stamp `channel` (packaged) → runtime name and launcher id;
`INDUS_DESKTOP_CHANNEL` / `--channel` → config `win.signtoolOptions.publisherName`,
`win.verifyUpdateCodeSignature: true`, staged `desktopName`; `dist-win.mjs` with an armed signer
and a placeholder publisher → error naming the file and key.

Files: `apps/desktop/scripts/channel-identity.cjs` (publisher lookup), `apps/desktop/electron-builder.config.cjs`,
`apps/desktop/scripts/dist-win.mjs`, `apps/desktop/scripts/stage-app.mjs`, new `apps/desktop/electron/identity.ts`,
`apps/desktop/electron/linuxLauncher.ts`, `apps/desktop/electron/main.ts`; tests beside each.

Edge cases / failure modes:
- Unpackaged (dev) run: no stamp → the stable names (`Indus`), as before; the launcher is never
  written outside a packaged AppImage anyway.
- Packaged with an unreadable stamp → canary names (the rule of `channel-identity.cjs`: an
  unlabelled build never takes the stable identity), so it can never overwrite the stable entry.
- userData is unaffected: Electron derives it from the packaged productName before main runs.
- Unknown channel in the config env → the existing `resolveChannel` error.
- identity.json missing, unparsable, or without a publisher for the channel → the config fails
  naming the file (a build must not ship a feed without a publisher).
- Placeholder publisher + no signer → build goes on (unsigned, manual update owner).
- Placeholder publisher + armed signer → refused before the build, message names file and key only.

Our design differences / decisions:
- W50-e-1 (D-16.1170): the runtime derives its identity from the build stamp's channel (the one declaration of
  what a build is, P20-37), not a value baked into the main bundle: `--skip-build` can reuse a
  bundle built for another channel, the stamp is always written per build. `electron/identity.ts`
  repeats the two base names and a test holds it equal to `channel-identity.cjs` for every channel.
- W50-e-2 (D-16.1171): the Windows publisher is read from `packaging/msix/identity.json` (`stable` / `canary`
  `publisher`), the one place the certificate subject is configured; no new owner value.
- W50-e-3 (D-16.1172): a signed Windows build with a placeholder publisher is refused (as `msix.mjs` refuses to
  sign with one); unsigned builds keep the placeholder, which fails closed.
- W50-e-4 (D-16.1173): the stamp's update owner on Windows stays `manual`; flipping it to electron-updater waits
  for the first signed run (owner item). Only the config half (publisher + verification on) lands.
- Left out: the notification centre's literal app name (`ambient/install.ts`), the Windows
  AppUserModelID, the `.deb` entry's StartupWMClass (electron-builder takes it from desktopName).

Tests we will write:
- identity: stable/canary/dev/no-stamp names; equal to `channel-identity.cjs` for every channel.
- launcher: canary file name, icon name, Name and StartupWMClass; stable unchanged.
- stage-app: desktopName follows the stamp's channel.
- config: `verifyUpdateCodeSignature` true and `publisherName` = identity.json's publisher per
  channel; a missing publisher throws; schema still valid.
- dist-win: armed signer + placeholder → refused; complete publisher or no signer → goes on.
