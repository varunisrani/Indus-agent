What it does (own words):
- `indus update` on a copy installed from the Termux APT channel (its `.install_method` stamp says
  `apt`, written by `build.sh`) now knows that kind by name: it is refused like the other installs a
  package manager owns, with the one instruction that works there — `pkg upgrade indus-agent` — and
  never tries to move the tree itself. Before, the unknown stamp fell through to `package` and
  told a phone user to reinstall with install.sh, which refuses Termux.
- The Termux build gets a `validate` stage between assembling the repository and signing it. The
  repository is first written unsigned, then `repo.py validate` checks the tree: the Release names
  exactly the two indexes with the right sizes and SHA-256, `Packages.gz` holds the same bytes as
  `Packages`, every stanza points at a pool file of the stated size and digest whose control
  matches the stanza, the tag's version is listed, and the tag's package has the on-device layout
  (everything under the Termux prefix, an executable `bin/indus`, the venv's python, the app's
  `src/indus/__init__.py`, and the `.install_method` stamp saying `apt` — the stamp the updater
  relies on). Only then does `repo.py sign` sign it. A tree that fails is never signed.

Inputs → outputs:
- `.install_method` = `apt` → `detect_kind` = `apt`; `indus update` (any of `-y`, `--check`) exit 1
  with the Termux message; `--plan` → `install_kind: apt`, `action: refused`, `reason` = message.
- `repo.py validate --out DIR --tag TAG` → exit 0 (prints the suite and count), 4 with one line per
  problem, 2 on bad arguments / tag.
- `repo.py sign --out DIR --tag TAG [--key-file F]` → validates first (4, nothing signed), then 3
  unsigned without a key or gpg, 0 signed (InRelease, Release.gpg, key.asc).
- `repo.py build ... --key-file F` (one call) validates before it signs too.
- `build.sh` stages: `... pack repo validate sign` (11); `repo` must end unsigned (exit 3), any
  other code stops the build; `validate` failure → exit 4; `sign` passes its 0 / 3 through.

Edge cases / failure modes:
- `apt` stamp with different case or a BOM → the version module already lower-cases and strips.
- A checkout with `.git` and an `apt` stamp is still `apt` (the stamp wins; the package manager owns
  the tree).
- Release missing, a third index named, an index missing or edited after the Release was written,
  a name that climbs out (`..`) → problems, exit 4.
- `Packages.gz` not gzip, or not the same bytes → problem; its decompression is bounded.
- Stanza missing Filename/Size/SHA256, a Filename that is not the pool path the control fields give,
  pool file missing / wrong size / wrong digest, a pool `.deb` whose control disagrees → problems.
- The tag's version not listed → problem (validating the wrong suite or a failed assembly).
- Payload: an entry outside the Termux prefix or with `..`, no `bin/indus` or not executable, no
  stamp or a stamp that is not `apt`, no venv python, no app package → problems.
- `sign` on a tree never assembled → exit 4 (Release missing), nothing written.

Our design differences / decisions:
- **W50-d-1** (D-16.1165) The message names the real package, `indus-agent` (`pkg upgrade indus-agent`, as the
  install guide already says); the brief's `pkg upgrade indus` would not find a package.
- **W50-d-2** (D-16.1166) `apt` is the Termux channel by contract (the only producer of that stamp is
  `scripts/termux/build.sh`), so the refusal speaks about Termux and `pkg`. Exit 1 like the other
  managed kinds (the reference's validation expects its own exit 2; ours keeps one code for every
  refusal).
- **W50-d-3** (D-16.1167) Signing moves out of the `repo` stage: `repo` assembles unsigned (exit 3 is its
  success), `validate` checks, `sign` signs (new `repo.py sign`). `repo.py build --key-file` keeps
  doing both in one call and runs the same validation before signing, so no path signs an
  unchecked tree.
- **W50-d-4** (D-16.1168) New exit code 4 for "the built repository is invalid", apart from 2 (bad input) and
  3 (unsigned), so CI logs say which. Problems are collected, not first-only.
- **W50-d-5** (D-16.1169) Every listed package's pool file is checked by size and digest; only the tag's own
  package is opened for the payload layout (older versions were checked when they were added).
- Left out: the in-container install / upgrade proof (dpkg + apt in a Termux rootfs, the reference's
  `check_apt.sh` role) — it needs docker and an aarch64 host; follow-up for the first lane run.
  `indus uninstall` and the dashboard's update hint keep their current handling of `apt`
