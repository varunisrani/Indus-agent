What it does (own words): on POSIX, `plan()` quietly turns two foreground shapes into tracked
background jobs: a command whose only backgrounding is one trailing `&`, and a foreground timeout
above `terminal.max_foreground_timeout` (600 s). On native Windows with a host-local backend
(`local`, which runs Git Bash there) background jobs cannot start (D-16.1043: `failed_start` with
the WSL2 text) and the schema no longer offers them (D-16.1082, whose timeout text already says
"maximum 600"). So both conversions there end in a refusal after approval, and the refusal texts
from the foreground guidance tell the model to use `background=true`, which that host does not
offer. On such a host `plan()` now:

- a trailing `&`: refused before anything runs, with a foreground hint (run it without the `&`;
  a server or watcher needs WSL2 or a Docker or SSH terminal backend);
- a timeout above the cap: runs in the foreground with the timeout capped at the cap, and the
  result says so (`timeout_capped`): what was asked, what was used, and that a longer job needs
  WSL2 or a sandbox backend;
- the other backgrounding shapes (inline `&`, nohup/disown/setsid, dev servers and watchers) are
  still refused, with texts that name no `background=true`;
- an explicit `background=true` keeps D-16.1043's refusal (D-16.1082 says so);
- sandbox backends on Windows and every other OS are unchanged.

Inputs → outputs: a `terminal` call + the scope's backend + the OS family → a `Plan` (foreground,
capped) or a `Refusal`; the foreground result gains `timeout_capped` when the cap applied.

Second part: `test_windows_starter_boots_and_stops_the_tree` (wave 47) slept 0.5 s and then read
the first word of the output as the shell's pid; on a busy box the first `echo` had not arrived
(failed once in 4 runs in wave 48). The test now waits until the reader thread has delivered the
lines it needs (the shell's pid and its background child's pid), with a generous deadline, and
also checks that the grandchild is gone, which is what the test name promises. The test's job
stand-in (`GroupJobs.pipe_available`) had its own window (bytes arriving between its byte count and
its `select` read as end of file); it now counts again before calling the pipe closed.

Edge cases / failure modes:
- Help / version calls with a trailing `&` (`srv --help &`) are not a trailing-`&` job on POSIX
  either; they fall to the guidance check exactly as on POSIX.
- A timeout equal to the cap is not capped (no note).
- A configured cap (`terminal.max_foreground_timeout`) is used, not the literal 600.
- The backend is the scope's configured one, looked up in the call's environment registry (the
  same rule as the schema override), so a Windows host whose profile uses Docker keeps POSIX
  behaviour.
- Test race: the reader thread appends chunks while the test polls; a chunk may hold a partial
  line, so the wait counts complete lines.

Our design differences / decisions:
- `plan(call, scope, *, foreground_only=False)`; `foreground_guidance(command, *,
  foreground_only=False)`; `TerminalTool.foreground_only(scope, environments)` shared with
  `schema_overrides`. Our names.
- Capping instead of refusing a long timeout: the offered schema already says "maximum 600" on
  that host, and a command that finishes early returns at once, so running it is the useful
  answer; the note tells the model a longer job was cut off (rc 124 at the cap).

## Decisions for the lead
- W50-c-1 (D-16.1161): on native Windows with a host-local terminal backend, `plan()` refuses a trailing `&`
  (foreground hint, WSL2 / Docker / SSH for servers) instead of turning it into a background job.
- W50-c-2 (D-16.1162): there, a foreground timeout above `terminal.max_foreground_timeout` is capped at it and
  the result carries `timeout_capped`, instead of a promotion to a background job.
- W50-c-3 (D-16.1163): there, the foreground guidance refusals (inline `&`, nohup/disown/setsid, servers and
  watchers) name WSL2 or a Docker / SSH backend instead of `background=true`.
- W50-c-4 (D-16.1164; tests only): the wave 47 starter test waits for its two pid lines (a real signal,
  15 s deadline) and checks the grandchild too; the `GroupJobs` stand-in counts the pipe again
  before calling it closed.
