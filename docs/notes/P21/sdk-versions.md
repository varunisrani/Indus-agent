# Interop record: vendor SDK and CLI versions (P21) Phase: 21 Owner: P21 slice B1 builder

Pins follow D-16.52: an exact version uploaded at least 14 days before the lock date
(`[tool.uv] exclude-newer = 2026-10-04T00:00:00Z`). Upload times were read from the PyPI JSON API on
2026-10-19; licences from each wheel's `METADATA`. Every SDK lives in its own extra and is imported
lazily inside its backend module, never at package import (the `indus` package must import with no
extra installed; CI installs none).

| Extra | Requirement | Uploaded | Licence | Import we use |
|---|---|---|---|---|
| `modal` | `modal==1.6.1` | 2026-10-03T16:05Z | Apache-2.0 | `import modal` (`App`, `Sandbox`, `Image`, `Client`, `modal.exception`) |
| `daytona` | `daytona==0.220.0` | 2026-09-29T11:34Z | Apache-2.0 | `import daytona` (`Daytona`, `DaytonaConfig`, `CreateSandboxFrom*Params`, `Resources`) |
| `vercel` | `vercel-sandbox==0.7.0` | 2026-09-23T16:46Z | MIT | `from vercel.sandbox.sync import SyncSandboxClient` (and models/errors from `vercel.sandbox`) |

Notes on the choices:
- `daytona==0.220.0` pins its six generated API clients at `==0.220.0` (same day); newer daytona
  releases (0.224+, 0.225) are inside the 14-day window.
- Vercel: the sandbox SDK ships as `vercel-sandbox` (namespace `vercel.sandbox`); the umbrella
  `vercel` package only depends on it. We pin the package we import, not the umbrella. Its licence
  is MIT (the open question the phase file raised about the reference's `vercel` 0.7.2 does not
  apply to this package). Its dependencies (`anyio`, `httpx2`, `pydantic`, `vercel-internal-core`,
  `vercel-oidc`) reach the lock only with the extra; the lead re-locks and checks their licences
  by hand (the licence guard walks `[project].dependencies` only, P05 landing note).
- The 0.7 Vercel SDK is a different shape from what the reference called: named, resumable
  sandboxes (`create_sandbox`, `get_or_create_sandbox`, `resume_sandbox`), session-bound processes
  (`run_process`, `create_process`), `sandbox.fs.*` file calls and `sandbox.snapshot()`. Process stdin
  is not supported by the SDK (`communicate(input=...)` raises), which is why Vercel stages stdin as a
  file (P21-03).
- Modal 1.6: `Sandbox.exec(*args, timeout=, workdir=, env=, text=)` returns a `ContainerProcess`
  (`stdout.read()`, `stderr.read()`, `stdin.write/write_eof/drain`, `wait()`, `poll()`,
  `returncode`); there is no per-process terminate, so an interrupt stops the process from inside
  the sandbox or terminates the sandbox. `Client.from_credentials(token_id, token_secret)` lets us
  hand the token pair to the SDK without putting it in the process env.
- Daytona 0.220: `sandbox.process.exec(command, cwd=, env=, timeout=)` returns
  `ExecuteResponse(exit_code, result)` (stdout and stderr together); files through `sandbox.fs`
  (`upload_file(bytes, path)`, `download_file(path) -> bytes`, `delete_file`, `get_file_info`,
  `set_file_permissions`). Errors carry `status_code`.

Vendor-standard credential names (D-16.22), read from the profile's secret store first, then its
env view; never passed through the process env to the SDK when the SDK takes them as arguments:
- Modal: `MODAL_TOKEN_ID`, `MODAL_TOKEN_SECRET` (also blocked from children:
  `MODAL_OAUTH_CLIENT_SECRET`, `MODAL_OAUTH_REFRESH_TOKEN`).
- Daytona: `DAYTONA_API_KEY` (or `DAYTONA_JWT_TOKEN` with `DAYTONA_ORGANIZATION_ID`).
- Vercel: `VERCEL_TOKEN` + `VERCEL_PROJECT_ID` + `VERCEL_TEAM_ID`, or `VERCEL_OIDC_TOKEN`.

CLI (Singularity backend, P21-04): Apptainer ≥ 1.2 and SingularityCE ≥ 4.0. Both take the same
flags for everything we use, so one argv serves both:

| Step | argv | Apptainer 1.2+ | SingularityCE 4.0+ |
|---|---|---|---|
| version probe | `<cli> version` | yes | yes |
| SIF build | `<cli> build --force <cache>.sif docker://<image>` | yes | yes |
| start | `<cli> instance start --containall --no-home [--writable-tmpfs \| --overlay <dir>] [--bind <h>:<c>:ro]… [--cpus N] [--memory NM] <sif> <name>` | yes (`--cpus`/`--memory` need cgroups v2 or root) | yes (same) |
| exec | `<cli> exec instance://<name> bash [-l] -c <script>` | yes | yes |
| stop | `<cli> instance stop <name>` | yes | yes |

Values for forwarded variables travel in the client's environment as `APPTAINERENV_<NAME>` /
`SINGULARITYENV_<NAME>` (both CLIs read their own prefix; `--containall` still honours them), never
on the command line (R02.7).
