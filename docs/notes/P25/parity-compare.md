What it does (own words): puts a flow's product capture next to the reference capture of the
same flow and lists what differs, aligned by exact step id. Kinds: `step-only-in-<side>`,
`step-failed-in-<side>`, `role-only-in-<side>` (structural kinds seen at a `wait_for` step on one
side only — accessibility roles for browser flows, card kinds and prompts for terminal flows,
message key paths for stdio and platform flows; names and text never compared; non-`wait_for`
steps never compared, because each app races its own update after an action) and `page-errors`.
Duplicate step ids or different origins are alignment failures: that flow is not compared and
counts as unclassified. Each divergence is classified with `rules.json`: a reference gap (its
step is listed as one the reference cannot do), intended (a rule matches scenario, kind and
subject and cites a D-id), else unclassified. `compare_all` writes `<flow>.compare.json` (summary,
counts) and `<flow>.divergences.json`; the runner exits 1 while anything is unclassified.
REA's own step-aligned comparison runs through its MCP tools on the same captures (the runner has
no MCP client); its result goes next to ours in `~/rea-lab/parity/indus/`.

Inputs → outputs: `python scripts/parity/compare.py PRODUCT REFERENCE [--rules FILE]` → JSON
result, exit 1 while unclassified; `runner.py --all --ref DIR [--out DIR]` → per-flow files and
the count; `docs/internals/parity-report-v1.md` → commands, versions, counts, limits.

Files: `scripts/parity/compare.py`, `tests/unit/parity/test_compare.py`,
`tests/fixtures/parity/captures/*.json` (synthetic, generated by us), `docs/internals/parity-report-v1.md`.

Edge cases / failure modes: REA results load wrapped (`normalized_result`) or bare; the
`scenario_start` step is skipped; an accessibility snapshot's quoted lines (`- 'button "…"'`) and
link URL lines are handled; a step only one side has and that failed there gives both kinds.
