What it does (own words): a Nix user can `nix run github:<owner>/indus-agent` (or add the flake as
an input) and get a working `indus` without PyPI (P5, D-16.14). The Python closure comes straight
from our `uv.lock` through uv2nix, so Nix installs the exact versions every other install method
uses. Because the Nix store is read-only, nothing can be installed lazily later; that is why there
are prebuilt variants that differ only in which optional extras they carry. The build guard of
P23-01 refuses wheel builds unless `INDUS_NIX_BUILD=1`, so the Nix build sets that variable for
our own package and nothing else. The in-app updater must refuse a Nix install ("Nix owns
updates"); detection already exists in `indus.cli.version.install_method` (a package under
`/nix/store` is `nix`), and P23-17 uses it.

Inputs → outputs:
- `flake.nix`: flake-parts; inputs `nixpkgs` (nixos-unstable), `flake-parts`, `pyproject-nix`,
  `uv2nix`, `pyproject-build-systems`, `home-manager`, every one following our `nixpkgs`; systems
  `x86_64-linux`, `aarch64-linux`, `aarch64-darwin`. Flake outputs: `packages.<system>.{default,
  minimal, messaging, tui, web}`, `devShells.<system>.default`, `checks.<system>.*`,
  `overlays.default`, `nixosModules.default`, `homeManagerModules.default` (modules: P23-14).
- `nix/variants.nix`: plain data (no nixpkgs needed) — the extras of each Python variant:
  `minimal` (none), `messaging` (minimal + the messaging adapter extras), `default` (messaging +
  the common portable extras). Plain data so Python tests and
  `nix-instantiate --eval` can read it without fetching anything.
- `nix/pins.json`: generated by `scripts/nix/pins.py` from the repo: the nixpkgs Python attribute
  (from `.python-version`), the Node.js attribute (from `package.json` `engines`), the pnpm
  attribute (from `packageManager`), the config stamp (`schema.CURRENT_VERSION`), plus one
  hand-kept value the Nix lane fills in: the fixed-output hash of the pnpm store
  (`pnpmDepsHash`, `null` until then, which builds with a fake hash so the lane prints the real
  one). `--check` fails when the file and the repo disagree.
- `nix/packages.nix`: the uv2nix workspace from `uv.lock` (wheels preferred), our package
  overridden with `INDUS_NIX_BUILD=1` and the built dashboard pages copied into
  `src/indus/web/static/` before the wheel is built (the pages are git-ignored, so a flake source
  never has them); one virtualenv per variant; `web` = the built dashboard (`apps/web/dist`),
  `tui` = the built renderer (`dist/entry.js` plus the `node_modules` it imports at run time);
  `default` wraps `bin/indus` with `INDUS_TUI_DIR` pointing at `tui` and Node at the end of
  `PATH`; `minimal` and `messaging` (servers) are the classic CLI and gateway with no Node. A devshell with the pinned Python,
  uv, Node and pnpm (uv told not to download Pythons and to use the Nix one).
- `nix/checks.nix`: builds every package and the devshell; `version` runs
  `indus --version` in a throwaway home and requires the version line and
  `Install method: nix`; `variant-extras` fails evaluation when a variant names an extra that
  `pyproject.toml` does not declare (read with `builtins.fromTOML`).

Files: `flake.nix`, `nix/packages.nix`, `nix/variants.nix`, `nix/pins.json`, `nix/checks.nix`,
`scripts/nix/pins.py`, `tests/unit/packaging/test_nix_files.py`, this note.

Edge cases / failure modes:
- a flake source excludes git-ignored files: the dashboard pages and TUI dist are built inside
  Nix, never taken from the checkout;
- the TUI bundle keeps its npm dependencies external (Vite SSR build), so the `tui` output ships
  `node_modules` next to `dist`; Node resolves them by walking up from `dist/entry.js`;
- `matrix-e2ee` is Linux-only and `python-olm` builds from its sdist with cmake, so it stays out of
  `default` until the Nix lane carries a build override for it; extras whose wheels bundle foreign
  binaries (`browser`, `voice`, `research`, cloud SDKs) stay out too and can be asked for through
  the modules' `extraPythonPackages` or a later variant;
- an extra renamed in `pyproject.toml` (P23-01 may restructure extras and add `all`) fails both the
  unit test and the `variant-extras` check instead of a confusing uv2nix error;
- the pnpm store hash cannot be computed without network: `null` builds with `lib.fakeHash`, and the
  Nix lane's first run prints the hash to record;
- the updater: an install whose package lives under `/nix/store` reports `nix`, and the dashboard's
  update hint already says to update through Nix.

Our design differences / decisions:
- Our names: package and flake outputs `indus-agent`, binary `indus`, env `INDUS_*`.
- Variant extras are plain data in their own file (tests read it without Nix); the reference keeps
  them inline.
- No desktop package, no sandbox package, no per-tool npm packages in the flake: the desktop is
  packaged by electron-builder (P23-15/16) and the sandbox images are Docker (P23-09).
- One shared pnpm dependency fetch for `tui` and `web`.

Tests we will write:
- flake inputs/follows/systems/imports; every imported file exists;
- variants: names, nesting (minimal ⊆ messaging ⊆ default), every extra declared in
  `pyproject.toml`; with `nix-instantiate` installed the file evaluates to the same data;
- every `.#<name>` named in `docs/` exists as a package (or a devshell/check);
- `nix/pins.json` is fresh (`scripts/nix/pins.py --check`), tampering fails the check;
- every `.nix` file parses (`nix-instantiate --parse`, skipped without Nix);
- `INDUS_NIX_BUILD = "1"` set on our package only;
- the Nix install kind: a package under `/nix/store` is `nix` and has an update hint (the updater
  refusal itself is P23-17's; see "Decisions").

## Decisions for the lead
- `default` = messaging (`discord slack mattermost google-chat qqbot dingtalk wecom feishu simplex
  buzz weixin yuanbao`) + `web docs pty dashboard acp`; `browser`, `voice`, `research`, `modal`,
  `daytona`, `vercel`, `discord-voice`, `matrix-e2ee` are left out (their wheels bundle binaries
  that need patching for Nix, an sdist needs cmake, or they are large). If P23-01 adds an `all`
  extra, `default` could become `[ "all" ]` once the Nix lane shows it builds — one line in
  `nix/variants.nix`.
- `flake.lock` is not committed: it can only be produced with network (`nix flake lock`). The Nix
  CI lane (or the owner) generates and commits it; until then inputs float on their default
  branches.
- `nix/pins.json` `pnpmDepsHash` is filled by the Nix lane (first build prints it).
- The Nix CI lane is not added to `.github/workflows/ci.yml` here (three slices share that file);
  the job to add is in the report (`nix flake check -L` on ubuntu + macOS runners with the
  Nix installer action pinned by SHA).
- The updater refusal for Nix (P23-17) should key on `install_method() == "nix"` and print "Nix owns
  updates: update the flake input (`nix flake update indus-agent`) and rebuild."
