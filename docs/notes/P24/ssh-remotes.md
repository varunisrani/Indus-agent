What it does (own words): an SSH connection entry (`user@host:port`, optional key file, remote
profile) lets the desktop use an Indus that runs on another machine reached over SSH. We drive the
system OpenSSH client, so `~/.ssh/config`, the agent, ProxyJump and hardware keys work as they do in
a terminal. One master connection per entry (`ControlMaster=auto`, `ControlPersist=300`) carries
every exec and forward; its control socket is a hashed file name under a short private directory so
the path — plus the 17 bytes OpenSSH appends for its temporary listener — stays within 104 bytes.
Every call is `BatchMode=yes` (no prompt can hang a spawned ssh: a key with a passphrase must be in
the agent) and `StrictHostKeyChecking=accept-new` (trust on first use; a changed host key fails
closed and the OpenSSH text is shown verbatim). Hard timeouts: connect 15 s, exec 20 s, forward
15 s; probe commands run under a remote 15 s watchdog so a hung remote command does not outlive our
local kill. Keepalive: a control `check` every 60 s; a dead master means reconnect, not retry in
place.

The remote serve: the app runs `indus serve ensure --json` over SSH with the connection's session
token written to the remote command's stdin (never argv, never the URL), forwards
`127.0.0.1:<local>` to the serve's port and from then on treats the entry like a remote URL
connection at that local address (tickets per dial, P24-29). A second forward makes the agent's
`localhost:N` links work in the preview: the preview asks for `localhost:N`, the app forwards a free
local port to the remote's N and rewrites the URL. A forward child that dies is restarted after
1 s, at most 5 times in a row; the count resets once a restart has stayed up; after the fifth the
connection reports dead.

Managed install/update: "Install / Update Indus on this host" runs `indus update` (or the install
script when missing) on the remote, detached, writing a marker file. Before each phase the app
writes a durable recovery record (`<userData>/ssh-update/<connection id>.json`: correlation id,
phase `draining` → `updating` → `restoring` → `done`, attempts, started/updated times). An app quit
or crash mid-update leaves the record; the next launch resumes from its phase (observe the remote
marker if it was updating, restart the serve if it was restoring) instead of starting a second
update; after 3 failed recovery attempts the record is given up and reported.

Remote execution boundary (R08.23): a client-only file never reaches the remote as a client path;
`uploadBytes` ships its bytes over the exec channel's stdin to a remote temp path the remote picks.

Inputs → outputs: `SshConnection.connect()`, `exec(command, {stdin?, timeoutMs?})` →
`{code, stdout, stderr}`, `forward(localPort, remotePort)` → `Tunnel`, `check()`, `close()`;
`SshUpdate.run(target)` / `SshUpdate.recover()` → outcome; errors `SshError{kind: unreachable |
auth-failed | host-key-changed | timeout | unknown, detail}`.

Edge cases / failure modes:
- host with control characters, a leading `-`, or a port outside 1–65535 → refused before spawn.
- key path with a newline or starting with `-` → refused.
- changed host key → `host-key-changed`, message names `ssh-keygen -R <host>` and carries the
  OpenSSH text; nothing is retried.
- passphrase/2FA needed → `auth-failed` saying to load the key into the agent.
- exec timeout → the child is killed, `timeout`, the master is considered dead.
- record exists for another correlation while a new update is asked → refused until recovered.
- record unreadable → quarantined as `<file>.bad`, treated as none.

Our design differences / decisions:
- Our control directory: `<userData>/ssh` when the budget allows, else `/tmp/indus-ssh-<uid>` (0700,
  owner checked).
- The remote session token is generated by the app per SSH entry and kept in the keychain.
- No Windows no-mux mode yet (OpenSSH on Windows lacks mux sockets): per-call options without
  ControlMaster when `platform === "win32"`, forwards each their own `ssh -N -L` child.

Tests we will write (fake `ssh` binary, our script):

- options: BatchMode, accept-new, ControlPersist=300, ConnectTimeout=15 always present.
