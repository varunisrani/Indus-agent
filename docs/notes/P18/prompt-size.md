What it does (own words): the System page can ask how large the system prompt of a profile (and,
optionally, of one stored session) is, and what makes it large. Nothing calls a model: the prompt is
built locally with the same builder chain a session uses (P04 builder under the P09 skills-index and
memory wrappers) and measured part by part.

Inputs → outputs: `GET /api/ops/prompt-size?profile=&session_id=&platform=` →
`{profile, session_id, platform, model, provider, estimate: "chars/4", system_prompt: {chars,
tokens}, request: {chars, tokens}, tiers: {stable, context, volatile}, sections: {persona,
context_files, memory, skills, tools}, tool_count, stored_prompt: {chars, tokens} | null,
warnings: [...]}` — every size is `{chars, tokens}` with tokens estimated as characters / 4 rounded
up (the estimate the context engine uses). `request` is the system prompt plus the tool schemas.
Helper: `indus.service.prompt_size.measure(scope, *, platform, session, cwd) -> PromptSize`
(`to_json()`), `session_facts(row)` turns a stored row into the inputs.

Files: new `src/indus/service/prompt_size.py`, `tests/unit/service/test_prompt_size.py`,
`tests/contract/web/test_prompt_size_route.py`; shared: `src/indus/web/routes/system.py` (route +
`ROUTE_LIST`), `apps/web/src/test/routes.generated.ts` (regenerated by its test), and a fix in
`src/indus/core/prompt/builder.py` (see the compare checklist) with one assertion in
`tests/unit/core/prompt/test_builder.py`.

Edge cases / failure modes:
- no session store yet, or no `session_id`: the profile's fresh prompt (memory and skills read from
  the files now);
- unknown session → 404 `session_not_found`; an unreadable store → the store's 503;
- a session with a stored prompt: its memory block is cut from the stored text (what the session
  really carries, as on resume) and the stored prompt's own size is reported beside the rebuilt one;
- no provider configured: model/provider are empty strings (the model-family gates then stay off);
- `platform` other than a short identifier → 400 `bad_platform`; default `cli`, or the session's
  source when a session is named;
- the stored folder of a session that no longer exists → the profile home is used for context files.

Our design differences / decisions:
- Answered synchronously as a read (GET), not as a background action: the build is local, takes
  milliseconds and the page wants numbers, not a log tail. The row's "run as background actions"
  stays true for doctor/backup/import/prune.
- Sizes in characters and estimated tokens (the task asks for tokens); no bytes.
- Tool schemas measured from the built-in, learning and cron tools selected for the platform
  (`platform_toolsets.<platform>`, else the `indus-<platform>` bundle); MCP and plugin tools are not
  started for a measurement, so they are not counted (listed in `warnings`).
- Plugin prompt sections and the external memory provider's block need their hosts running and are
  not built here either (also in `warnings` when configured).

Tests we will write:
- unit: sections add up; a persona and a context file grow their sections; memory notes and a
  skill grow memory/skills; tools count and size follow the toolset selection; a stored prompt's
  memory block wins over the files; no provider → empty model; JSON shape.
- contract: the route over the real app (profile scope, `?session_id=` known / unknown, bad
  platform), in `ROUTE_LIST` and the generated list.

## Decisions for the lead
- GET and synchronous instead of an action (above). Easy to change: wrap `measure` in
  `_start_job` and log `to_json()`.
- Route name `/api/ops/prompt-size` (the reference's path) with GET.
