What it does (own words):

- Prompts (`review/prompts.py`): three review instructions — memory only, skills only, both — built
  from small blocks written fresh. Memory: each fact goes to exactly one store (`user` = who the user
  is and how they want to be helped; `memory` = facts about the environment and the work), or the
  reply says nothing is worth keeping. Skills: be active; prefer, in order, patching a skill used in
  this session, then an existing class-level skill, then a support file under such a skill (with a
  one-line pointer in its `SKILL.md`), and only then a new class-level skill. Lessons are rules
  attached to the step they change, with the reason; no incident stories, PR/issue numbers, dates or
  quotes; nothing that depends on the machine's setup or a passing failure; overlaps are mentioned
  in the reply for the curator; never delete. Read-before-write: view a skill (or the exact support
  file) in this review before changing it. A closing line names the tools this review may use
  (memory only when allowed). `/refine` focus text is appended as the user's priority.
- Summary (`review/summary.py`): lines built from the fork's new tool rows (its own calls only).
  `display.learning_notices`: `off` → no lines and no event; `on` (default) → one generic line per
  kind: "Memory updated" / "User profile updated" once per store, "Skill <name> created" or
  "Skill <name> improved" once per skill; `verbose` → the same lines plus a preview of at most 200
  characters (the saved text, the new span of a patch, a file path and its start). Staged writes
  (`staged: true`) and failed or rolled-back ones (`success` not true, batch `operations_applied`
  false) are never reported as done.
- One completion log line per review (requests, input/output/cache-read tokens, result kinds, stop
  reason) and the session event `learning.review.done {kinds, summary_lines}` for CLI/TUI/gateway
  (P15 renders it in chats).

Inputs → outputs: kinds + focus + allowed tool names → prompt text; fork rows + mode → lines;
lines → `LearningReviewDone` event.

Edge cases / failure modes:
- tool content that is not JSON, or not an object → ignored;
- a tool row whose call is not in the fork's own assistant rows → ignored (never re-reports history);
- an exception while summarising → logged, empty lines (the writes already happened);
- unknown mode → `on`.

Our design differences / decisions:
- the "on" lines are generic per kind/skill instead of echoing the tool's own message;
- the golden prompt file is generated from the module (`--update-golden`), so a change shows as a
  diff in review.

Tests we will write:
- golden prompt file stable; n-gram check passes on it (tooling.checks);
- add + patch in `on` mode → two generic lines; staged patch omitted; failed batch omitted;
- `verbose` includes a preview of at most 200 chars;
- `off` emits no event; `on` emits `learning.review.done` with kinds and lines.
